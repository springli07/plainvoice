# 测试、效果评估与发布标准

测试通过说明实现符合已覆盖的行为约定，不能据此宣布文章“更像人写的”。本文件把工程验证与文风效果验证分开；下面的盲评是建议的后续实验，不是已经执行的结果。

## 工程测试

已有测试应覆盖可导致真实失败的边界：

- 短语前缀没有出现时不误罚共享 token；前缀出现后正确调整完成 token。
- 权重有界，正向增强需要明确配置，重复增强受到限制。
- 批次序列独立，提示词不污染生成历史，输入 logits 不被意外修改。
- tokenizer 不匹配、无效配置、词表越界和不可信序列拒绝使用。
- 诊断位置对应原文，代码与引用不作为普通文风命中。
- 改写后的数字、引用或代码变化被发现；后端超时、错误响应和保留失败不会被呈现为成功。
- CLI 与 HTTP 接口执行真实应用路径；未配置模型时诊断仍然可用，生成能力明确不可用。

运行：

```bash
uv sync --frozen --extra dev --extra tokens
source .venv/bin/activate
pytest
ruff check .
python -m build
```

具体通过、跳过和未执行项应以本次运行记录为准。使用替身 tokenizer 或模拟 logits 的测试验证控制算法，不等于完整模型推理测试；模拟 HTTP 响应也不等于已经取得真实服务商访问权限。

## 建议的真实效果实验

准备有使用权的评估材料，包含说明文、技术文档、个人叙述等你实际需要的体裁。训练与评估按文章或任务隔离，避免同一材料的相似版本出现在两侧。

对每个写作任务，固定模型版本、输入事实、长度预算、采样参数和随机种子安排，比较：

| 实验组 | 目的 |
|---|---|
| 原有生成流程 | 建立可复现基线 |
| 相同写作指令 | 单独测量提示词带来的变化 |
| 相同指令＋短语偏置 | 测量动态偏置的额外影响 |
| 相同指令＋语料偏好 | 测量训练偏好是否迁移到新文本 |

如对比上游 Skill，应保持用户请求、允许改写的范围与评价材料一致，并记录多轮交互成本。不要把上游的研究数字直接作为这里的基线。

隐藏实验组标签并随机左右顺序，让评审分别回答：哪篇更清楚、更符合作者意图、更自然；哪篇出现事实变化、重复、空洞替换或不合题材。不能仅以规则命中变少作为胜出标准，因为删除内容也能降低命中数。

同时记录：

- 双盲或至少盲化的偏好票数、平局数、评审人数和评审一致性。
- 数字、引文、专有名词、否定与限定条件的保留情况。
- 新增重复、异常措辞、篇幅变化和请求失败。
- 生成耗时、模型版本、tokenizer 标识、偏置参数和运行环境。

报告样本量与不确定性，按体裁分别看结果。参数应在验证集上选择；测试集用于最终评估，不能反复调参后仍当作独立证据。

## 发布前检查

工程版本至少要能够安装、运行离线分析、启动工作台并通过已有测试。若宣传某个真实模型的生成能力，应额外记录该模型的实际推理结果、资源需求和已知失败样本。

若宣传“文风质量提升”，需要公开对应任务、评估方法和实际结果。在此之前，准确的描述是“提供可测试的文风控制机制”，而不是“已证明优于原项目”或“成熟到适用于所有写作场景”。
